# Generative UI in Course Chat

**Status:** Proposed. Decisions 1 to 4 below need a yes before step 1 starts.

**Goal:** Let the chat answer with interactive components, not only text. A student who asks "quiz me on lecture 5" gets a working quiz inside the answer. One who asks "what's due this week?" gets a deadlines card with countdowns and links to each assignment. Text answers stay exactly as they are.

**Inspiration:** a reel by @mudasirdevv ("generative ui is lowkey sick"). Current practice, from LangChain, assistant-ui and CopilotKit docs: the model picks from a fixed catalog of components the developer built and fills in their props. It never writes markup. That is the pattern here.

**Approach:** Display tools in the existing chat loop. `backend/chat.py` already runs a provider-neutral tool loop (`search_course`, `recall_memory`, `forget_memory`, up to `MAX_TOOL_ROUNDS = 4`). Each new tool:

1. takes structured arguments from the model,
2. builds the component's data **in code** from real sources (Canvas, the study generator), never from the model's own text,
3. sends a `{"ui": {...}}` event in the same NDJSON stream as `{delta}`,
4. returns a short text result so the model knows what the student is seeing and doesn't repeat it.

On the app side, `Answer.tsx` looks the component name up in a fixed map and renders it. An unknown name renders nothing. Nothing the model writes becomes HTML, which matters in a Tauri webview.

## What exists that this reuses

| Need | Already there |
|---|---|
| Tool loop, any provider | `chat.answer`, `llm.LLMProvider.stream_chat` (OpenAI tool format) |
| Quiz generation with a grounding check | `study.start` / `study.generate`: every question cites its passage, unsupported ones get dropped (docs/plans/2026-10-03-study-artifacts.md) |
| Quiz UI, progress saving | `QuizView.tsx`, `POST /courses/{id}/study/{aid}/progress` |
| Assignments with real submission status | `canvas.list_assignments` + the normalization in `main.py:_handle_list_assignments` |
| Due-date formatting and countdowns | `app/src/assignmentStatus.ts` (`formatDue`, `daysUntil`, `statusText`, `countdownPercent`) |
| Streaming and saving turns | `main.py` stream loop (`append_turn` on `done`), `sidecar.ts:askQuestion`, `SavedTurn` |

So the quiz in chat **is** a study artifact. It's generated by the same checked pipeline, it shows up in the Study panel afterwards, and its progress is saved the same way. No second quiz generator.

## The event contract

New NDJSON line, sent when the tool runs (before the text that talks about it):

```json
{"ui": {"id": "ui-1", "component": "deadlines", "props": { ... }}}
```

- `component` is one of a fixed set: `"deadlines"`, `"quiz"` (later `"flashcards"`).
- `props` is built by the backend and checked against the component's shape before it's sent.
- The `{citations, grounded}` line and `{done}` don't change.
- `main.py` collects `ui` events like it collects deltas and saves them on the turn: `turn["ui"] = [...]`. `SavedTurn` gets `ui?: UiBlock[]`. Old turns just don't have it (no migration, per the pre-launch rule).

## Decisions

1. **Placement.** Blocks render **below the answer text, above Sources**, in the order the tools ran. Putting them inline at a marker in the text is possible later, but it complicates streaming and the citation renumberer. Recommended: below.
2. **Saved deadlines: snapshot or live.** The block saves the assignments as they were when asked. Countdowns are computed from `due_at` at render time, so "due in 2 days" stays correct. The submitted/late status can go stale, though, so the saved block shows "as of <date>" and an Open action that goes to the live assignment view. Recommended: snapshot.
3. **Quiz size in chat.** Default `fewer` (5 questions), `medium` difficulty, topic from the student's words. The model can pass `count` and `difficulty` only when the student asked for them. Generation takes 10 to 40 s (first live runs in the study plan), so the block shows a generating state and the text answer doesn't wait for it.
4. **When the model may call a display tool.** Only when the student asks for practice, a quiz, deadlines or what's due, or asks a planning question ("what should I work on?"). Never on a plain content question. At most one call per display tool per turn, **enforced in code** (a second call gets "Already shown above."). Prompt alone didn't hold for the forced-search rule, so this one goes in code from the start.

## Steps

Stacked PRs, one per step, each with its proof in the description (same style as the Quiet ledger PRs). Backend steps prove with `uv run pytest`. Frontend steps prove with `npm run build` plus screenshots from the proof harness (`app/.proof/`, rebuild it if the worktree lost it).

### 1. Tool errors go back to the model

`chat.py:run_tool` has no error handling. Today that's only search and memory, but display tools call Canvas over the network, so a timeout would kill the whole answer mid-stream.

- Wrap `run_tool` in `try/except Exception`: log it, return `"The <tool> tool failed: <short reason>. Answer without it, or say what you couldn't get."`
- Tests in `tests/test_chat.py`: a tool that raises, with a scripted provider. The answer still streams and ends with `{done}`.

Proof: test output.

### 2. Backend: `ui` events and the `show_deadlines` tool

- Move the assignment normalization out of `main.py:_handle_list_assignments` into `canvas.py` (`normalized_assignments(course_id)`), so the route and the tool share it. The route behaves the same.
- `chat.py`: `DEADLINES_TOOL` with args `{"days": int (1 to 60, default 14), "include_submitted": bool}`. In code: fetch, filter to the window, sort by `due_at`, cap at 12. Undated assignments go last, like `splitAssignments`.
- `answer()` gets a `canvas_assignments: Callable[[], list[dict]] | None` argument (injected like `memory`, so tests don't touch Canvas). When it's `None` the tool isn't offered.
- Emit `{"ui": {"id", "component": "deadlines", "props": {"as_of", "days", "assignments": [...]}}}`. Tool result for the model: one line per assignment (name, due date, status) so it can add advice ("start the essay first, it's worth the most").
- Prompt: a short "Display tools" section with decision 4's rules.
- Per-turn cap from decision 4.
- `main.py`: collect `ui` events, save them on the turn.
- Tests: tool offered only with the callable; window filtering and sorting; the `ui` event comes before the final line; a second call is refused; the saved turn has `ui`; Canvas failure goes through step 1's path.

Proof: test output, plus one live `curl` against a real course showing the NDJSON with a `ui` line.

### 3. App: block registry and the deadlines card

- `sidecar.ts`: `UiBlock` type, `ui?` on the stream event and on `SavedTurn`. `askQuestion` hands `ui` events to the caller.
- `ChatPanel.tsx`: append blocks to the current turn as they arrive; read them from saved turns.
- `Answer.tsx`: a `ui` prop and a `BLOCKS: Record<string, Component>` map. Unknown names render nothing.
- `components/app/blocks/DeadlinesBlock.tsx`: rows with due date, countdown, status text (reuses `assignmentStatus.ts`, red only for late or due within a day, per Quiet ledger), an "Open" action that goes to `AssignmentView`, and "as of" on saved turns. Empty state: "Nothing due in the next N days."
- Styles in `styles.css` with the existing tokens. No new dependencies.

Proof: build; screenshots of the live answer streaming in, the finished card, a saved chat reopened, the empty state, and one late assignment.

### 4. Backend: `show_quiz` tool

- `QUIZ_TOOL` args: `{"topic": str, "count": "fewer"|"standard", "difficulty": ...}`. Validated with `study.check_options` (clamps and rejects like the Study panel).
- Calls `study.start(..., kind="quiz")` in the background and emits `{"ui": {"component": "quiz", "props": {"artifact_id", "topic", "count"}}}` right away. The text answer doesn't wait.
- Tool result for the model: "A 5-question quiz on <topic> is being written from the course and will appear below your answer. Don't write the questions yourself. Say in one line what it covers."
- If the course has no indexed material, it returns that to the model and emits no block.
- Tests: `study.start` called with the right options (stubbed), no block when nothing is indexed, cap of one per turn, saved turn keeps the `artifact_id`.

Proof: test output; live run showing the artifact file under `courses/<id>/study/` and in `GET /courses/{id}/study`.

### 5. App: quiz block

- `blocks/QuizBlock.tsx`: polls the artifact (same as `StudyPanel` does today) while it's `generating`. Shows "Writing 5 questions from your course…", then renders `QuizView` compactly inside the answer. On `error` it shows the error text with a retry that starts a new artifact.
- `QuizView` gets a `compact` prop: no back link, narrower layout, "Open full quiz" button that opens the normal study view. Progress goes through the existing progress route, so finishing in chat shows as finished in the Study panel.
- An artifact deleted from the Study panel renders "This quiz was deleted." in the old chat.

Proof: build; screenshots of generating, first question, answered with rationale, results, reopened saved chat with progress kept, deleted state.

### 6. Check it doesn't over-trigger

- Add ~20 questions to the ask-modes eval set (docs/evaluations/2026-09-23-ask-modes/): 10 that should trigger a display tool ("quiz me on…", "what's due", "what should I do this weekend") and 10 that look similar but shouldn't ("what is on the quiz on Friday?", "when was the midterm?").
- Run them on the default model and one other provider. Report trigger precision and recall in the eval folder. Tighten the prompt if a plain question gets a block.

Proof: the report.

## Later, not in this plan

- `show_flashcards`: same path as the quiz, mostly wiring once step 5 exists.
- Concept maps / mindmaps: needs a new generator with its own grounding check, which is a separate plan.
- Inline placement at a marker in the text (decision 1).
- Streaming partial props (a quiz that shows questions as they pass the check).

## Risks

- **Latency and cost.** A quiz is 2 to 4 extra LLM calls. It runs only when asked for, in the background, and it's the same cost as making one from the Study panel.
- **Over-triggering.** Covered by decision 4's code cap and step 6's eval.
- **Provider differences.** Smaller models misuse tools more. The tool schemas stay small (2 to 3 args, enums where possible) and step 6 runs on two providers.
